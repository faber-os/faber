- **The name:** only `Faber` / `faber` / `FABER` (CLAUDE.md rule 10). The GitHub org and npm scope are `faber-os`, because the bare names are taken.
- **Light is the default theme** (Mikkel, 2026-10-15), as D31 said. An explicit `theme = "system"` in settings.toml still follows the screen.

- **Settings batch 1 notes:** wall-clock text is always `en-GB` (English UI, D44), so 12-hour shows "2:30 pm". Larger text scales text and rem spacing, not px chrome (taskbar, icons, window min sizes). Diagnostics strip paths and Bluetooth names, but USB serial numbers can still show in port ids. The time-zone list comes from the browser (some legacy names). Angles setting removed until something shows an angle.

Default names of new items ("New folder") are translated. Window titles are read at display time (`DesktopController.titleOf`), so open windows follow a language change; windows that name themselves (documents) keep their names.

- **Core hang (fixed 2026-10-16): a lock-order deadlock.** Listing packages (`GET /api/v0/packages`, also after an app install) held the machine lock and then took the apps lock (`app_problems`), while reconciling apps (the sweeper every 200 ms, or a request) holds the apps lock and then takes the machine lock. Every request needs one of them, so the core froze (CI and local e2e, ~1 in 30 runs of apps.spec). Found by the new lock watchdog, which named both holders and waiters. Fix: app problems are read before the machine lock. Guard against the whole class: `Watched` locks have ranks (apps 1 < machine 2) and debug builds panic on a wrong-order take, naming both locks; a test lists packages with an app installed. **Rule: never take the apps lock while holding the machine lock.** Also kept: the watchdog (logs holder + waiters of a lock held > 2 s), a bounded app stop with step reporting, the sweeper's non-waiting app check, core logs on stderr; and fixed on the way: an app handle joining its own thread, the window hearing \"drive ended\" before its lease was released, a racy supervisor test.

## Phase 1 notes (2026-10-15)
- **Serial protocol was ambiguous** (found by the shell agent): no "opened" reply, unclear which errors end a session. Fixed at the protocol level: `serial-opened` is sent before any data (the machine opens the port, the WebSocket announces it, then reading starts), and only `serial-closed` ends an open session. Rules in docs/api.md.
- **The shell's list of server message types is keyed by the generated union**, so a new message type in the core is a TypeScript compile error until the shell handles it (it had silently dropped `serial-opened`).
- **Comments in parts.toml:** a comment block directly above a part goes with it on removal; anything above a blank line stays. New parts go after trailing comments (a comment-only file keeps its header on top).
- **Open:** capability `info` (e.g. LiDAR range min/max) has no place in the API yet, so the scan viewer fits the farthest point. Add `info` to `ProvideInfo`/`SignalInfo` when connector manifests carry it (Phase 3).
- **Open:** the LD19 connector doesn't judge rotation speed (the datasheet range wasn't verified), only silence and corrupted packets.
- The shell agent ran a broad `taskkill` on `node.exe` while testing; Mikkel's other node processes appeared to survive, but that's unverified.
