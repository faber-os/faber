# Decisions

Short records of *why* things are the way they are, so they don't get re-debated. Status is
**accepted** (Mikkel approved), **proposed** (written by an AI agent, waiting on Mikkel), or
**superseded by Dnn**.

| # | Decision | Status | Why (short) |
|---|---|---|---|
| D01 | Faber is general purpose. SENNEP is its first *app* and its field test, not its purpose. | accepted | More useful to others, and it forces a clean core/app split. SENNEP keeps the scope honest: build only what a real project needs. |
| D02 | HA-OS-style appliance (Linux underneath, never visible) plus a web desktop. No custom kernel, no drivers. | accepted | A kernel or drivers would be years of work. The value is in the hardware model and the UX. |
| D03 | Exactly four concepts: **core, connector, tool, app**. Exactly two package types: connector and app. | accepted | HA's add-on / integration / platform confusion. See [glossary.md](glossary.md). |
| D04 | Apps depend on **capabilities**, never on connectors. | accepted | It makes apps hardware-independent, and it's how the ecosystem scales. |
| D05 | A fixed, versioned starter set of capabilities (41, in [capabilities.md](capabilities.md)). New ones only through registry review. | accepted | Ad-hoc capabilities would fragment apps (HA entity domains, Node-RED's untyped payloads). |
| D06 | Capability data shapes follow ROS `sensor_msgs`/`geometry_msgs`, SI units, µs timestamps. | accepted | Battle-tested shapes, and a cheap ROS bridge later. |
| D07 | Third-party code runs as **WebAssembly** (Wasmtime, Component Model, WIT). Native connectors allowed, but marked unsandboxed. | accepted | None of HA, Viam, CasaOS or Node-RED sandboxes extensions. This is a real differentiator, and it's safer for a store. Native covers camera/ML. |
| D08 | Declarative (manifest-only) connectors as a first-class kind. | accepted | ESPHome shows most simple sensors need no code. Lowers the bar for contributors. |
| D09 | The core is one Rust process. WASM packages run inside it, in isolated instances. | accepted | Simple, small, debuggable, runs on a dev PC. Native connectors are the only extra processes. |
| D10 | The port manager owns all hardware access and arbitrates claims. | accepted | Enables permissions, conflict detection and the built-in tools. No other platform has it. |
| D11 | Real-time stays on microcontrollers via **bridges** (FaberLink). The Pi side is supervisory. | accepted | Linux and WASM aren't real-time. Matches SENNEP's Pi ↔ Mega split. |
| D12 | Safety primitives in the core: leases, safe states, e-stop, update lock, bridge heartbeat. | accepted | Things that move need it, and nobody else provides it. |
| D13 | Config is TOML files. The UI edits the same files. | accepted | Avoids HA's YAML-vs-UI split. Git-friendly. TOML over YAML: no indentation traps, native in Rust. |
| D14 | One shell for remote browsers and the attached screen (Cage + Chromium kiosk). | accepted | Mikkel wants the desktop on an attached screen. One codebase. |
| D15 | Network: mDNS `<name>.local` + hotspot fallback + built-in Tailscale. Public tunnel opt-in, with a warning. | accepted | Mikkel asked for local, Wi-Fi/online and Tailscale. Exposing something that moves to the internet must be a deliberate choice. |
| D16 | Auth and roles in the core from v0.1. | accepted | Retrofitting auth is how insecure products happen. |
| D17 | Ship a real image (rpi-image-gen, Debian Trixie) with A/B updates (Rugix Ctrl, tryboot) from the **first public release**. Develop on a PC before that. | accepted | Umbrel rebuilt from install script to image because a script couldn't update the kernel. Retrofitting A/B means re-flashing. Buildroot/Yocto are too heavy for one person. |
| D18 | Store = GitHub registry repo, PR-reviewed, CI-validated. Namespaced third-party registries by URL. | accepted | Umbrel/CasaOS model, no server to run, free. Namespacing prevents id collisions. |
| D19 | Licence: **Apache-2.0** for everything (core, SDK, first-party packages), with a `NOTICE` file ("Copyright 2026 Mikkel Ryborg Blom"). Store packages may carry their own licences. | accepted | Open source with no open-core and no noncommercial clause (CasaOS stalled, ZimaOS paywalled, Umbrel is noncommercial). Anyone may use it, including commercially, as long as the credit stays. Apache adds patent protection over MIT. |
| D20 | Not a home-server OS (no media/NAS/Docker-app focus). | accepted | CasaOS and Umbrel already do that well. The gap is hardware. |
| D21 | Apps never provide capabilities. | superseded by D24 | — |
| D22 | Faber is designed on its own terms first. SENNEP is then **retrofitted** onto it as the field test. FaberLink is designed fresh, not derived from SENNEP's protocol (answer to Q4). | accepted | SENNEP's Pi ↔ Mega protocol is only early pre-work, and SENNEP is still at the first-prototype print stage. |
| D23 | Personal notes and explainers live in `private/` (git-ignored), never in the public docs. | accepted | Explainers written for Mikkel (e.g. what WASM is) aren't project documentation. |

| D24 | Apps may publish **derived signals**: computed data (pose, map, nearest obstacle) under the app's own name, typed with a capability shape. They can never claim ports or accept commands. A role accepts a derived signal only if the app's manifest opts in. (Answer to Q7.) | accepted | Lets apps share computed data without a fifth concept. SENNEP tests it by publishing its pose. |
| D25 | Name: **Faber** (Latin "maker"). The image is called "Faber OS" in prose. Identifiers follow the rules in [research/naming.md](research/naming.md) so a rename stays a search and replace. | accepted | The working name AlmaOS collided with AlmaLinux OS. Faber has no OS/robotics collision, but the bare `faber` crate, npm scope and GitHub name are taken, hence `faber-os` for the org and npm scope. |
| D26 | Wire format (core ↔ shell, core ↔ native connectors, recordings): **MessagePack**, with **JSON** as a debug fallback (`?format=json`). Both come from the same Rust types, and WIT stays the only schema. (Answer to Q3.) | accepted | Compact and fast, mature in Rust and the browser, no second schema language. JSON keeps debugging readable. |
| D27 | Signing (answer to Q5): **phase 1:** HTTPS + sha256 pinned in the registry at review, plus **minisign**. The Faber maintainer holds two keys: the **OS-image key** (offline) and the **registry-index key**. **Later: TUF** (`tough`) directly, for expiry, rollback protection and key rotation. No GitHub-account-based trust (no SSH-key or attestation trust model). | accepted | A GitHub account is not a trust anchor. minisign is the simplest thing that protects the OS image and the index. TUF is the proper long-term design for a store. |
| D28 | Shell: **Svelte 5 + Vite**, built as a static single-page app served by the core (no Node.js on the machine). The shared widget kit (`<faber-gauge>`, `<faber-scan-view>` …) comes later as **Lit web components**, so app UIs in any framework can use it. Future docs website: Astro Starlight. (Answer to Q2.) | accepted | Fine-grained reactivity suits a desktop full of live values better than React's re-rendering. Small and readable for contributors. Web components keep app authors free to choose their own framework. |
| D29 | Capability rules and the lease as defined in [capabilities.md](capabilities.md): `info`, named instances, *built from*, leased vs shared commands, every command renews a lease, every lease has a deadline, operators can always take over, `laser-scan` supports even bins *and* raw points, servo safe state is configurable (default hold). | accepted | Agreed with Mikkel. Covers SENNEP's 20 needs plus 21 common maker parts. |
| D30 | **Ease of use is the first design principle** ([principles.md](principles.md)): plug and play, detect-then-suggest, no terminal for normal use, errors that say what to do, examples tested in CI and explained. Faber is the next step after Arduino, before bare Raspberry Pi. | accepted | Mikkel's goal: anyone with a bit of technical curiosity can use it. Arduino's weak spot is outdated, unexplained examples. |
| D31 | Look: **Aluminium**. Neutral, Mac-like greys, soft rounded windows, a deep teal accent, light by default with a dark mode. Logo: a hex nut with an F cut out. Replaces the shell agent's "forge" theme. | accepted | Mikkel disliked the dark orange look and the "name + dot" logo. Mac look, Windows layout. |
| D32 | The LD19 demo recording is an **optional sample**: not listed by default. Files offers "Add sample recordings", which copies it into Recordings. | accepted | Showing it everywhere made Faber feel premade. It stays useful for trying Faber without hardware. |
| D33 | New term **accessory**: built-in programs that aren't about hardware (Files, Notes, Settings). Amends D03: four concepts plus accessories, still only two package types. | accepted | "Tool" stays hardware-focused, so its meaning doesn't drift. |
| D34 | Files see only Faber's **home folder** by default. **Developer settings** can allow the whole machine, behind a strict warning that must be confirmed. Once login exists (Phase 6), only admins can turn it on. | accepted | Ease of use and safety by default, power for technical users (D30). |
| D35 | Recordings are a real feature: the serial monitor records into Recordings, and every recording there is a replay port. | accepted | Replays are useful for development and demos, but they must be the user's own data, not a canned demo. |
| D36 | **Simulation at the capability level, built into the core.** A *simulated part* has the same name and capability as a real one; only its source changes (`simulate = "manual"` or `"world"` instead of `connector` + `port`). The *world* is 2D and kinematic only (pose and velocity, no forces). Connectors never need a simulator. New capabilities must bring a simulation recipe through registry review. | accepted | Apps depend on capabilities (D04), so simulation is universal and nobody writes per-part simulators. Build the software before buying the hardware. 2D kinematics covers wheeled machines and every spatial capability without becoming a physics engine. |
| D37 | New **Phase 2, "Drive before you wire"**: actuator capabilities, leases and the e-stop, simulated parts, and the world with prebuilt realistic layouts. The later phases move down one. A **world creator** comes later. | accepted | Needs no hardware (motors aren't wired yet), and gets safety tested in simulation before real motors. |
| D38 | Shell design, picked per element by Mikkel from the variants canvas: teal nut logo with a light/dark lockup; white (light) or dark icon plates with coloured glyphs; menus with a header for what was clicked; taskbar with the nut left, programs centred and clock right, in a small and a large size, with **pinning**; **tabbed windows** (Notes, Files); a grid start menu with one power button; Files with a details list, small and large icons (Ctrl + wheel / pinch zooms) and a sidebar; Settings with a grouped sidebar and **six styles**, each with a light and a dark version. | accepted | Mikkel chose each element himself, after the first Aluminium redesign didn't match the preview. Styles are generated from a few numbers, so every style is complete and contrast-tested in both modes. |
| D39 | **Removable disks** (USB sticks, SD cards) are their own places in Files (`disk-<name>:/`), found on every port scan. They have no Trash: deleting there is for good, after a confirm. Moving between a disk and home waits for copy. External hard drives (fixed disks to Windows) are not listed. | accepted | Mikkel asked for disks in the Files sidebar. A Trash folder on someone's stick would be a surprise, and moving off a stick that may be pulled out half-way is risky without copy. |
| D40 | **Settings are machine-wide**, also display settings (larger text, reduce motion, contrast). Each has a `System` default that follows the browser or screen, like the theme. Settings is grouped You / This machine / Hardware / Advanced, and shows no empty "coming later" sections. | accepted | Mikkel: "whole". The attached screen and a laptop stay in agreement, and the kiosk can be set up from a laptop. |
| D41 | **Backups** are `.zip` files in `home:/Backups` (parts.toml, settings, Notes; Recordings only when ticked, with their size shown). Restore checks `parts.toml` before anything changes. Installed connector packages are included too (2026-10-15), and restore re-checks each one like a fresh install before anything is put in place. | accepted | Mikkel picked a Backups folder. Recordings are large, so they are opt-in. A folder in home can be downloaded, copied to a disk, or restored from Files. |
| D42 | **Time is the machine's.** Clocks, file dates and log times show the machine's own time zone (from its OS), in every browser, so a remote viewer sees the machine's local time. Settings can override the time zone. 12/24-hour clock is a setting. | accepted | Mikkel's answer to Q7. A robot in another room or country should show its own time. |
| D43 | **Units are display-only.** The core, the API, recordings and apps stay SI, µs and radians (D06); the shell converts for display (metric/imperial, degrees/radians). | accepted | Capabilities stay comparable; one conversion point. |
| D44 | **Translatable now, English only shipped.** Every shell text comes from an English catalogue; a translation is a plain file (one per language) that works as soon as it is there. A checker lists what a translation is missing. No language picker shows until a second language is installed. Translations become store packages later. | accepted | Mikkel: support it now, ship English, and a checker for untranslated words. Extracting strings now is cheaper than after more windows exist. |
| D45 | **The machine has a name** (`settings.machine.name`, default `faber`), a valid host name. It names the browser tab, About and backups, and becomes `<name>.local` on the Pi image. Resetting settings keeps it. | accepted | Mikkel's answer to Q3. Storing it now means no rename later. |
| D46 | **Confirm before driving** (Phase 2): before anything moves the motors, Faber asks once per session. On by default; a switch to turn it off comes later. The e-stop can never be turned off. | accepted | Mikkel's answer to Q6. |
| D47 | **The Arduino flasher speaks the bootloader protocols itself** (STK500v1 for Uno/Nano, STK500v2 for the Mega), in Rust (`sdk/rust/flash`), instead of bundling avrdude. It only flashes on an explicit request with a confirm, checks the chip's signature before writing anything, and verifies by reading back. | accepted | One binary on every OS with nothing to download, and the protocol code is tested against simulated bootloaders. Not yet run on a real board. |
| D48 | **Battery levels** come from per-chemistry thresholds in the core (Li-ion/LiPo low 3.5 V, critical 3.3 V per cell; LiFePO4 3.0/2.8; NiMH 1.1/1.0; lead-acid 11.8/11.5 V per 12 V), with a little hysteresis so a wobbling voltage doesn't flood notices. A level change raises a notice (log + shell toast). The FaberLink library keeps the same numbers, checked by a test. | accepted | Typical datasheet values for resting cells, not measurements. SENNEP's 3S pack: low 10.5 V, critical 9.9 V. |
| D49 | **App state is held by the core**, one store per app shared by its logic and its windows, saved at most once a second and before backups and shutdown. Editing `state.toml` by hand while the core runs has no effect. | accepted | A window and the logic must see the same state; the logic used to overwrite what the UI could have written. |
| D50 | **A window driving through its app's logic is an explicit, core-enforced intent**, not app state. A command role says `drive = "window"` when its logic may drive it only while one of the app's windows drives through it; that window gets the D46 confirm and the shell's Stop bar, and the core itself ends the logic's lease on Stop, close, or 300 ms without a heartbeat. `drive = "logic"` (the default) stays background control, enabled by turning the app on. Window ↔ logic traffic is a live channel that is never saved. | accepted | The SENNEP window drove by writing to app state, skipping D46 and the Stop bar. Open trade-off: an app that never declares `drive = "window"` can still steer from its window without a confirm; the Install window says which kind each role is. |
| D51 | **SENNEP's own code lives in the SENNEP V2 repo**: its FaberLink Mega firmware and the SENNEP app. Faber keeps general examples (the wall-follower app, the FaberLink example sketches). `examples/apps/sennep` moves there when the retrofit starts. | accepted | Faber is general purpose (D01); SENNEP is its first user, not part of it. |
| D52 | **`@faber-os/shell` is not published to npm yet.** `faber new app` copies the SDK into each app; publishing waits until the app API is stable (around Phase 7). The FaberLink Arduino library also stays inside the Faber repo until it is listed in the Arduino Library Manager. | accepted | Publishing is public and hard to undo; nobody needs it yet. |
| D53 | **Users and roles (Phase 6a):** viewer (watch, press Stop), operator (drive, leases, release the e-stop, simulate, serial monitor, app windows, home files, display settings), admin (everything else: users, parts, installs, flashing, backups, developer settings, the machine's name, time and screen role). Every route has one access rule (`core/src/api/access.rs`, enforced by a test). First run creates the admin. Sessions are in memory (a core restart signs browsers out); API tokens and the attached screen keep working. **Stop needs no sign-in.** A host check (`421`) and an origin check on writes and WebSockets. `--no-auth` only on loopback. Details and the nine points to confirm: `docs/auth.md`. | accepted | Mikkel accepted all nine points in docs/auth.md (2026-10-16). Each is one table entry or flag to change later. |
| D54 | **The Arduino editor** compiles with `arduino-cli` (Faber's own copy, else the PATH, else the Arduino IDE 2's; pinned 1.5.1; installed only after a confirm) and uploads with Faber's own flasher (D47). **Same-code check:** after each upload Faber records the board (USB serial number, or port + vid/pid marked not unique), the sketch, a build id (SHA-256 of the sketch's files and the board) and a SHA-256 of the programmed bytes, and keeps an exact copy of what it flashed. A FaberLink board reports its build id at the end of HELLO_ACK (live, no reset); any board can be read back and compared on request (it resets the board). Without proof Faber says "needs a check", never "still runs". The code is opened as itself only if it is unchanged, otherwise as a copy. A board compiled by a newer editor can't talk to an older core. | accepted | Mikkel accepted (2026-10-16). Mikkel's idea (a hash of what was flashed) plus a live id for FaberLink boards, so the common case needs no reset. |
| D55 | **The core has its own HTTPS client** (ureq 3.4 with rustls), so far only to download arduino-cli and check it against its published SHA-256. | accepted | Mikkel accepted (2026-10-16). One binary on every OS; the alternative is calling the system's `curl`. |
| D56 | **Pi buses (Phase 6b):** I²C, SPI and GPIO are ports (`i2c-<bus>`, `spi-<bus>.<cs>`, `gpio-<line>`); an I²C bus is claimed per address, everything else whole. The Linux backends use `i2cdev`, `spidev` and `gpiocdev` (the GPIO v2 character device, never sysfs) because the workspace forbids `unsafe`. The I²C scan only reads (never i2cdetect's quick write) and skips addresses parts use. The GPIO panel switches an output only through its part, with a lease and the D46 confirm; it never drives a pin no part owns. | accepted | Mikkel accepted (2026-10-16). Safe by default on a machine that may have other things wired; crates instead of hand-written ioctls keep `unsafe` out. |
| D57 | **Two modes for a board's code** ([wiring.md](wiring.md)): *code mode* (your own sketch) and *guided mode* (Faber writes the sketch from a `board.toml` plan, suggests and checks pins, shows the wiring). Guided boards get a `my_code.h` tab Faber never overwrites; "Take over the code" turns a guided board into code mode, one way; a FaberLink `PINS` message lets any board report its pins; the pin-map format covers the Pi's 40-pin header and pin providers (PCA9685, ADS1115 …) too. First part templates: the research's first wave of 12; `FaberMotor` gets driver shapes (EN + IN1 + IN2, two PWM inputs, PWM + DIR). | accepted | Mikkel: "continue with your recommendations". Ease of use for beginners, full control for everyone else. |
| D58 | **FaberLink PINS and motor shapes as built:** `PINS` (0x05) goes just *before* its part's `PART`, carries `analog_base` (the board's A0 number) and pins by one global role table (pwm, dir, en, in1, in2, stby, trig, echo, signal, sense); an unknown role shows as "Pin". `FaberMotor` takes a driver constant (`DRIVER_EN_IN1_IN2`, `DRIVER_TWO_PWM`) or the old PWM+DIR form; stop = every speed and direction pin low; a shared STBY/enable pin is raised at `begin()` and never lowered. On a BTS7960 that stop *brakes* (low-side on); Mikkel chose braking for SENNEP (shortest stop on Stop or a lost link). | accepted | Mikkel accepted it as built (2026-10-16), braking included. |
| D59 | **First-wave part classes as built:** buttons, switches and end stops are `digital-in@1`; bumpers and IR obstacle modules get a new **`obstacle@1`** (so an app looking for a button never gets a bumper). A servo's safe state is whatever it is set up for (hold by default, D29) and it starts released. `Part::capabilityId()` is pure virtual: a custom part deriving from `faberlink::Part` adds one line. Servo, encoder, IMU and ToF classes live in optional headers so sketches don't pay for them; FaberImu talks to the MPU6050 over Wire directly. | proposed | Agent's choices, all recommended. Open: how Faber compiles sketches that need a library it doesn't ship (Servo): install on demand (downloads) or use the IDE's library folder. |
| D60 | **The wiring diagram is drawn, not drawn by hand** (docs/wiring-diagram.md): a guided board's plan becomes a diagram that lays itself out around the board and routes its own wires (no overlaps, hops at crossings, buses per net), with the plan's checks on it and a Build tick list. Parts get a `[drawing]` table (size, pin positions in mm, optional SVG). | accepted (changed) | Mikkel 2026-10-17: (1) Faber ships SVGs for its own parts, packages may bring theirs, as recommended. (2) **One diagram for the whole machine**, Pi and boards together, linked right there (USB, UART). (3) **Breadboards are in**: parts plug into holes. Also: a right-click menu with "Connect to…" another part. Built first as a standalone app (`tools/wiring-lab`) on localhost, moved into the shell when it's right. |
